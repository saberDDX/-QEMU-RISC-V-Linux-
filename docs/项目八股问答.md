# 项目八股问答：30 题

配合《项目完整流程与学习路线》和实际代码使用。每题先用自己的话回答，再补充“本工程哪个文件、什么结果”。标为“必会”的题优先；“理解”题先掌握职责与排查思路。

## Q01【必会】为什么需要交叉编译？

宿主是 x86_64，目标是 RISC-V。交叉编译器在宿主运行，生成目标架构代码。QEMU 本身是宿主程序，而固件、Linux、BusyBox 和 bsp_demo 是目标代码，因此不能都用同一个默认编译目标。

**本工程**：看 scripts/env.sh 和各 build 脚本；在目标 `uname -m` 得到 riscv64。`readelf -h` 检查程序 Machine；两者分别是产物属性和实际运行环境的证据。

**追问：换个工具链前缀就一定兼容吗？** 不一定，还要看指令集、ABI、编译器/链接器能力、库和项目配置。

## Q02【必会】ARCH、CROSS_COMPILE、O=、-j 分别做什么？

ARCH=riscv 选择内核的架构代码与配置；CROSS_COMPILE 是 gcc/ld/objcopy 等工具的前缀；O= 指定独立输出目录；-j 控制并行构建任务数。

**本工程**：scripts/build-kernel.sh 使用 Linux GCC 11 的绝对前缀，输出到 output/build/linux，默认 JOBS=4。修改 ARCH 不是修改 CPU 硬件，-j 也不是目标系统的 CPU 数量。

## Q03【理解】newlib、glibc、sysroot 是什么？

newlib 常用于裸机/RTOS，底层系统接口需由相应环境提供；glibc 是本工程 Linux 用户态使用的 C 库。sysroot 是编译器查找目标头文件和库的一套根目录，不能把它误当作正在运行的目标根目录。

**本工程**：裸机固件使用 medany newlib；BusyBox/bsp_demo 使用 RISC-V glibc 2.41。内核不链接用户态 glibc。OpenSBI/U-Boot 虽使用 Linux 前缀工具链，也不能据此认为它们链接了 Linux 用户态 libc；实际由各组件构建参数控制。

**追问：为什么重建 newlib？** 原库与高地址固件的地址模型不匹配，出现 R_RISCV_HI20 溢出；重建 medany 库后固件可链接和运行。此处不需要背重定位公式。

## Q04【必会】QEMU 在这里做什么？与真实板卡有什么区别？

QEMU 作为宿主进程，模拟目标 CPU、内存、串口、存储及其他设备。本工程使用上游自定义 quard-star 机型，用 TCG 执行 RISC-V 指令，可以验证软件启动链路与配置。

它不能替代真实板卡的电气、时序、DDR 初始化及硬件性能验证。第一个项目提供真实 RK3576 外设经历，第二个项目补充最小系统构建和启动调试。

**本工程**：scripts/build-qemu.sh、scripts/run.sh，目标 model 为 riscv-quard-star,qemu。

## Q05【必会】QEMU 常用参数如何解释？

-M 选机型；-m 配置内存；-smp 配置虚拟 hart/CPU 数；-accel tcg 选择软件翻译执行；-drive 连接存储后端；-device 添加设备；-serial 连接串口后端；-display none 不创建显示前端。

**本工程**：1 GiB、8 hart，Linux 可用 7 个；-global virtio-mmio.force-legacy=false 使用现代 virtio MMIO 接口。只需懂实际用到的参数，不必背 run.sh 中每个字符串。

## Q06【必会】从上电到 U-Boot 谁加载谁？

本次 QEMU 从 Mask ROM 开始，Mask ROM 根据 SD 启动设置读取 lowlevelboot。lowlevelboot 从固件 SD 镜像按约定位置加载 OpenSBI、DTB、trusted_domain 和 U-Boot。OpenSBI 完成其初始化及域设置后，按上游配置交接给 U-Boot 等后续软件。

**本工程**：上游 mask_rom/main.c、lowlevelboot/main.c 的 sd_boot()，以及 scripts/build-firmware.sh / pack-images.py。早期固件与板级实现是复用上游，不是自己从零写的。

## Q07【必会】OpenSBI 与 U-Boot 有什么区别？

OpenSBI 在本平台 M 态提供 SBI 服务，例如定时器、跨 hart 协作、复位等标准接口的实现，具体能力以平台为准。U-Boot 负责更高层的启动策略：读取启动文件、设置参数并进入内核。

二者处于不同职责层次；不能简单说“OpenSBI 就是另一个负责读根文件系统的 U-Boot”。本工程使用两者，是上游既有启动设计。

## Q08【理解】RISC-V 的 M/S/U 是什么？

M 是机器态，权限最高；S 是监督态，通常运行内核；U 是用户态，通常运行应用。本工程 OpenSBI 在 M 态，U-Boot 配置为 S 态，Linux 在 S 态，BusyBox/bsp_demo 在 U 态。

**证据**：U-Boot CONFIG_RISCV_SMODE、OpenSBI Domain 的 next-mode 和启动日志。不是所有平台的 Bootloader 都一定在 S 态。

**追问：为什么 -smp 8 但 Linux 只有 7 个 CPU？** 上游将 hart7 分配给 trusted_domain，Linux 域不使用它；不是少启动了一个本应属于 Linux 的 CPU。

## Q09【必会】DTS、DTB、驱动的关系是什么？

DTS 是可阅读的设备树源码，DTB 是编译后的二进制描述。它们描述硬件资源与属性，驱动是实际执行设备操作的代码。设备树可以帮助设备创建、资源传递和驱动匹配，但 DTB 不是驱动本身。

**本工程**：脚本先 cpp 处理 include，再 dtc 编译上游 DTS；复用现有板级描述，没有新增外设节点实验。第一项目中的 compatible 匹配知识可直接用于理解这一层。

## Q10【必会】boot.cmd、boot.scr、bootcmd 有什么区别？

boot.cmd 是本项目维护的 U-Boot 脚本文本；mkimage 将它打包成可被 source 执行的 boot.scr；bootcmd 是 U-Boot 环境中的默认引导命令。

**本工程**：Distro Boot 扫描 virtio 第一分区并找到 /boot.scr。它执行 load/setenv/booti。这些是 U-Boot 命令，不能在 Linux Shell 中直接按同样语义使用。

## Q11【必会】bootargs、root、console 是什么？

bootargs 是交给内核的命令行。root=/dev/vda2 指定本工程根文件系统位于 virtio 磁盘第二分区；console=ttyS0 指定串口控制台。

**本工程**：configs/boot.cmd 设置 bootargs，并用 booti 引导内核；最终结果在目标 /proc/cmdline 确认。不能只看宿主文本或某个时刻的 U-Boot 环境，就断言最终传入了什么。

**追问：设备树 chosen/bootargs 也有值，怎么办？** 存在多处来源时应核对 U-Boot 的实际传参/修正路径，以目标 cmdline 验证。本工程执行脚本设置环境 bootargs，前后结果已经实测。

## Q12【必会】你改了什么参数，如何证明生效？

只在 baseline/custom 启动脚本的对照中把 loglevel=7 改成 loglevel=4，保留 root 和 console。重新打包 boot.scr 和磁盘后重启。

**证据**：cmdline 分别有 7 和 4；/proc/sys/kernel/printk 第一项分别是 7 和 4。脚本没有再用 dmesg -n 覆盖阈值。

**追问：loglevel=4 的含义？** 内核消息级别 0—7，数值越小越紧急；正常规则下控制台输出级别小于当前阈值的消息，4 通常对应输出 0—3。降低阈值不代表环形缓冲区不再记录较低优先级日志，不能据此声称完成性能优化。最早期参数解析前仍可能出现少量输出。

## Q13【必会】defconfig、.config 和 y/m/n 是什么？

defconfig 是配置起点，.config 是实际展开的构建配置。y 是编入内核，m 是模块，n 是不构建。olddefconfig 根据已有配置补全新项与依赖。

**本工程**：quard_star_defconfig 起步，关闭 FTRACE/GCC_PLUGINS；实际配置保存在 evidence/linux.config。源码中“有某驱动”不等于本次已构建或已验证它。

## Q14【理解】根磁盘驱动为什么不能随便全做成模块？

模块需要先被某个已运行的用户空间加载。如果模块本身放在尚未挂载的根文件系统里，就无法靠它来完成挂根。可将启动必需驱动内建，或通过恰当的 initramfs 先提供并加载模块。

**本工程**：不传 initrd，virtio 块设备和 ext4 等挂根所需能力为内建。没有声称实现 initramfs 启动方案。

## Q15【必会】Image、vmlinux、DTB、rootfs 分别是什么？

Image 是引导使用的内核二进制；vmlinux 是内核 ELF，带本次调试所需符号/调试信息；DTB 描述硬件；rootfs 提供 init、库、命令和配置。

**本工程**：U-Boot 从 FAT32 第一分区读 Image/DTB；Linux 挂第二分区为根；GDB 从宿主读 output/build/linux/vmlinux。不能用一个只剩原始 Image 的文件替代带符号 vmlinux 做相同的源码调试。

## Q16【必会】BusyBox 是什么？与内核有什么关系？

BusyBox 是用户态多调用程序，将许多常用命令合并为 applet，通过链接名或参数分派，适合最小系统。它不是内核，也不等于完整 GNU 用户空间。

**本工程**：提供 init、sh、mount、cat、uname 等。/sbin/init 和 /bin/sh 可最终指向同一个 BusyBox 二进制，但执行职责不同。

## Q17【必会】/proc、/sys、/dev 为什么要准备？

/proc 提供进程和部分系统信息；/sys 提供设备模型等接口；/dev 放设备节点。本工程分别挂载 proc、sysfs、devtmpfs。它们不是把宿主对应目录直接拷贝进 rootfs。

**本工程**：程序读 /proc/uptime，参数验证读 /proc/cmdline；rcS 在程序执行前挂 proc。目标根目录中预先建 /proc 目录，只是提供挂载点，不等于已挂载 proc。

## Q18【必会】你的 C 程序具体做什么？

解析 manual/autostart 参数；用 uname 获取运行系统的架构和内核版本；读取 /proc/uptime 第一列；输出后退出。错误路径检查返回值并输出错误，文件读取结束调用 fclose。

**本工程**：app/bsp_demo.c。默认不传参数按 manual 处理；它不常驻、不控制硬件、不做性能采样。代码中的 autostart 字符串由 rcS 传入，不是应用自动识别开机状态。

## Q19【必会】为什么程序文件存在，却可能报“not found”？

先确认路径和执行权限，再检查架构、ELF 的 PT_INTERP 动态解释器及所需共享库。动态解释器缺失时，即使可执行文件本身存在，exec 也可能返回 ENOENT；具体 Shell 的报错形式可能不同。

**本工程**：readelf -h/-l/-d 的记录在 evidence/bsp_demo.elf.txt。解释器为 /lib/ld-linux-riscv64-lp64d.so.1，目标 rootfs 放入配套 RISC-V 库；没有把 x86 库当作目标库。

## Q20【理解】静态链接与动态链接的基本区别？

静态链接把所需库代码链接到产物；动态链接在运行时由解释器等机制加载共享库。实际体积和部署取舍要看依赖与使用场景，不能绝对说某种一定更快或更小。

**本工程**：BusyBox 与应用采用动态方式，部署匹配库；没有安排静态/动态对比实验。不要把工具链启动时附带的通用环境测试写成该项目独立性能成果。

## Q21【必会】PID 1、init、inittab、rcS 怎么联系起来？

内核创建并运行负责初始化的 PID 1 路径，随后 exec 用户态 init；exec 不会因此重新分配 PID。本工程最终执行 /sbin/init，即 BusyBox init。它读取 inittab，sysinit 项调用 rcS；rcS 挂系统设施并运行应用。

**证据**：GDB 看到了 /sbin/init 参数；目标 ps 看到了 PID 1 的 init；启动日志显示 rcS 和程序输出。Shell 是后续交互入口，本次不由 Shell profile 触发应用自启动。

## Q22【必会】为什么程序要放在 proc 挂载之后？如何证明自启动？

程序需要打开 /proc/uptime，只有 proc 正确挂载后，该接口才可用。rcS 按这一依赖顺序组织初始化。

**证据**：没有输入手动运行命令前，串口已经出现 mode=autostart；进入 Shell 后另外运行 bsp_demo manual，分别保存输出。仅手工调用 `bsp_demo autostart` 不能单独证明已实现开机自启动。

## Q23【必会】rootfs 目录与磁盘镜像有什么区别？

output/rootfs 是宿主上的内容暂存目录；rootfs.ext4 是包含这些内容的 ext4 文件系统镜像；disk.img 是有分区表并容纳启动和根分区的整盘镜像。

**本工程**：第一分区 96 MiB FAT32 放 Image/DTB/boot.scr；第二分区 256 MiB ext4 放用户空间。只改暂存目录不自动改变已打包镜像，更不会自动改变正在运行的目标。

## Q24【理解】booti 中间的 '-' 是什么？没有 initrd 怎么启动？

该位置表示 initrd 参数，'-' 表示本次没有提供 initrd。U-Boot 仍传内核和 DTB，Linux 依靠内建驱动找到 root=/dev/vda2 并挂根。

**本工程**：底层固件的 sd.img 与 Linux 的 virtio disk.img 不同；没有使用 RK3576 项目中的 Ubuntu/initrd 启动方案，不能直接套用第一项目的流程。

## Q25【必会】改不同内容，需要重建哪些部分？

改应用：重新编译应用、部署到暂存 rootfs 并重做磁盘。改 rcS：更新 rootfs/镜像。改 boot.cmd：mkimage 重新生成 boot.scr、更新启动分区。改内核配置/代码：重建 Image 后更新磁盘；若调试还要使用对应的 vmlinux。

**本工程**：make-images.sh 会重建完整磁盘，因此执行前先关机并保留需要的目标内文件。只改 loglevel 无需重新编译 Linux。

## Q26【必会】QEMU gdbstub、KGDB、应用 gdbserver 有什么区别？

QEMU gdbstub 在模拟器中控制虚拟 CPU，在 Linux 尚未运行时也可连接；KGDB 是内核侧调试机制；应用 gdbserver 通常在目标用户空间运行并调试进程。

**本工程**：只验证 QEMU gdbstub，加载 vmlinux 看内核启动。不把它写成真实 RK3576 KGDB/JTAG 调试，也不把 GDB 基本反汇编当成已定位实际驱动故障。

## Q27【必会】-S、-s、hbreak、next、bt、detach 是什么？

-S 暂停 QEMU 的 vCPU；-s 是 GDB TCP 1234 监听的简写，本工程用显式 -gdb tcp:127.0.0.1:1234。hbreak 请求硬件辅助断点；next 按源码单步并越过调用；bt 查看调用栈；detach 结束远程调试，让本次 QEMU 继续运行。

**本工程**：早期使用 hbreak，避免预先修改尚未加载/映射的内核代码；next 实测从 start_kernel 的函数入口到 941 行。不要把 next 与汇编单步 stepi 混为一谈。

## Q28【必会】你设置了哪两个断点，分别证明什么？

start_kernel：证明进入 Linux 的 C 启动入口，查看了源码、PC/SP、栈和 init_task.comm。run_init_process：查看准备执行的 init_filename，实际是 /sbin/init。删除断点并 detach 后，系统继续进入 Shell，原应用运行正常。

**证据**：evidence/gdb-startup.log、boot-after-gdb.log。第二次断点可能切换 GDB 线程；默认 gdbstub 线程是虚拟 CPU/hart 视角，不能直接把线程编号当 Linux ps 的 PID。汇编栈根处“frame did not save the PC”不自动等于栈损坏。

## Q29【必会】你遇到了什么真实问题，怎么处理？

选择两个讲清即可：

1. 高地址裸机固件链接失败：发现 newlib 地址模型不匹配，重建 medany 库并重新链接，后续固件运行成功。
2. Linux GCC 14 组合先在 ftrace 初始化 panic，关闭后仍在早期初始化停顿；保存日志、检查状态，最终切换官方 Linux GCC 11.1/binutils 2.36.1，完成正常启动。没有证据把全部根因归结到某一条编译器源码 bug。

还处理了免 root 镜像制作、U-Boot 独立输出目录 Logo 路径、BusyBox tc 与新版 UAPI 的兼容问题。都在构建适配记录，不必每个都背。

## Q30【必会】你的个人贡献和项目边界是什么？

基于开源 Quard Star，完成固定版本、云环境构建与兼容适配、镜像集成和启动验证；个人定制包括内核参数、自编 C 程序、初始化自启动以及可复现 GDB 启动调试入口与记录。

上游提供虚拟板卡、早期固件、Domain、U-Boot 板级支持和驱动。本项目没有新写外设驱动、真芯片 DDR 初始化、从零 BSP 移植、真实板卡调试或性能优化指标；音频探测失败也没有列为通过。

**面试表达**：“第一个项目侧重真实 RK3576 外设驱动与采集；第二个侧重 RISC-V 最小系统构建和启动调试，两者相互补充。”
