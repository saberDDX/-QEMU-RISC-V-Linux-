## 1. U-Boot 启动脚本

[configs/boot.cmd](../configs/boot.cmd#L1)

```text
echo Quard Star BSP: loading kernel and device tree from virtio disk
load virtio 0:1 ${fdt_addr_r} /quard_star.dtb
load virtio 0:1 ${kernel_addr_r} /Image
setenv bootargs 'root=/dev/vda2 rw console=ttyS0 earlycon=sbi loglevel=4'
booti ${kernel_addr_r} - ${fdt_addr_r}
```

逐行理解：

1. echo：在引导串口输出标记，帮助判断 boot.scr 已被执行。
2. 第一条 load：从 virtio 设备 0、分区 1 读取 DTB，放到 fdt_addr_r 对应的 RAM 地址。
3. 第二条 load：从同一分区读取 Image，放到 kernel_addr_r。
4. setenv bootargs：准备传给内核的字符串。root/console 保留，定制点为 loglevel=4。
5. booti：传入内核地址、无 initrd 的标记、DTB 地址，进入内核引导流程。

这里传的是 RAM 地址，不是文件在磁盘里的偏移。文件系统负责按文件名找到内容，U-Boot 读出后放进 RAM。

本板级默认变量来自上游 qemu-quard-star.h：kernel_addr_r=0x80000000，fdt_addr_r=0x82000000。实际日志还显示 U-Boot 按内核要求移动 Image 到 0x80200000。这是平台加载约定，不要求背地址，更不应把所有 RISC-V 平台都当成同一布局。

### boot.cmd 怎样变成 boot.scr

[scripts/make-images.sh](../scripts/make-images.sh#L20) 中的实际命令：

```bash
"$OUT/build/uboot/tools/mkimage" -A riscv -O linux -T script -C none -a 0 -e 0  -n 'Quard Star BSP boot' -d "$bootcmd" "$OUT/images/boot.scr"
```

-d 指定脚本文本，-T script 指定脚本镜像类型。mkimage 加上 U-Boot 能识别的镜像封装，不是把 U-Boot 命令交叉编译成 Linux 程序。这里的 -O linux 也是镜像元数据，不能据此说脚本文本是 Linux Shell 语法。

参数对照见 [evidence/bootargs.diff](../evidence/bootargs.diff#L1)；从 baseline 到 custom 只把 loglevel=7 改为 4。

## 2. 自己的 C 程序

[app/bsp_demo.c](../app/bsp_demo.c#L1)

```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <string.h>
#include <sys/utsname.h>

int main(int argc, char **argv)
{
    struct utsname info;
    double uptime = 0.0;
    const char *mode = argc == 2 ? argv[1] : "manual";
    if (argc > 2 || (strcmp(mode, "manual") && strcmp(mode, "autostart"))) {
        fprintf(stderr, "usage: %s [manual|autostart]\n", argv[0]);
        return 2;
    }
    if (uname(&info) < 0) {
        perror("uname");
        return 1;
    }
    FILE *fp = fopen("/proc/uptime", "r");
    if (!fp) {
        perror("/proc/uptime (proc must be mounted)");
        return 1;
    }
    int count = fscanf(fp, "%lf", &uptime);
    fclose(fp);
    if (count != 1) {
        fputs("cannot parse /proc/uptime\n", stderr);
        return 1;
    }
    printf("[BSP_DEMO] started mode=%s\n", mode);
    printf("[BSP_DEMO] machine=%s kernel=%s uptime=%.2f seconds\n",
           info.machine, info.release, uptime);
    return 0;
}
```

按六段阅读：

1. `_POSIX_C_SOURCE`：请求相应 POSIX 接口声明；不是设置 CPU 架构。
2. `struct utsname info` / `uptime`：保存运行时系统信息和开机时长。
3. `mode` 与参数检查：无参数默认 manual；只接受 manual 或 autostart。strcmp 相等返回 0；非法参数输出用法并返回 2。
4. `uname(&info)`：取当前系统信息，失败时 perror 输出 errno 对应说明并返回 1。info.machine 是架构，info.release 是内核 release。
5. `fopen`/`fscanf`/`fclose`：读 `/proc/uptime` 第一项，检查是否读到一个 double，随后关闭文件。scanf 的 `%lf` 对应 double*。
6. `printf` 与返回值：先打印明确标记，再输出 machine/release/uptime；`%.2f` 是两位小数显示，不代表计时精度达到了某个性能指标。正常返回 0。

关键区分：这是一次性程序，不是后台守护进程。`autostart` 参数只说明调用者传入了这个词；实际自启动证据还必须是开机尚未输入命令就出现输出。

### 应用如何构建和安装

[scripts/make-images.sh](../scripts/make-images.sh#L10) 中的实际命令（节选）：

```bash
riscv64-linux-gnu-gcc -Wall -Wextra -Werror -O2 -g  "$PROJECT_DIR/app/bsp_demo.c" -o "$OUT/bsp_demo"
install -m755 "$OUT/bsp_demo" "$OUT/rootfs/usr/bin/bsp_demo"
```

-Wall/-Wextra 启用常见警告，-Werror 将警告作为构建错误，-O2 优化，-g 保留调试信息。install 同时复制并设置执行权限。

本工程 PATH 里的 GCC 包装器补上正确 sysroot，避免重定位后的 Debian 目标库链接脚本仍去不存在的系统绝对路径查找文件。不是用宿主 gcc 默认编译。

目标依赖记录：[evidence/bsp_demo.elf.txt](../evidence/bsp_demo.elf.txt#L1)。解释器和库要放到目标路径，不能只在宿主上存在。

## 3. init、自启动与 Shell

[rootfs/etc/inittab](../rootfs/etc/inittab#L1)

```text
::sysinit:/etc/init.d/rcS
console::askfirst:-/bin/sh
::ctrlaltdel:/sbin/reboot
::shutdown:/bin/umount -a -r
```

BusyBox inittab 形式是 `id:runlevels:action:process`；BusyBox 对 runlevels 不采用完整 SysV runlevel 语义，本文件留空。

- `::sysinit:`：系统初始化时执行 rcS。
- `console::askfirst:`：在 console 上按回车后启动交互 Shell；不是靠它调用 bsp_demo。
- `-/bin/sh` 的前导 '-'：以登录 Shell 方式运行，配合 /etc/profile 设置环境和提示符。
- shutdown 项：关机时卸载/只读重挂文件系统；ctrlaltdel 项指定对应动作。

[rootfs/etc/init.d/rcS](../rootfs/etc/init.d/rcS#L1)

```bash
#!/bin/sh
mount -t proc proc /proc || exit 1
mount -t sysfs sysfs /sys || exit 1
mount -t devtmpfs devtmpfs /dev 2>/dev/null || test -c /dev/console || exit 1
mkdir -p /dev/pts /run /tmp
mount -t devpts devpts /dev/pts
mount -t tmpfs tmpfs /run
hostname quard-star-bsp
printf '\n[INIT] proc/sys/dev ready; starting bsp_demo\n'
/usr/bin/bsp_demo autostart || printf '[INIT] bsp_demo FAILED\n'
printf '[INIT] initialization complete\n'
```

执行顺序：

1. proc：让 /proc/uptime、/proc/cmdline 等内核接口可用。
2. sysfs：挂载设备模型接口。
3. devtmpfs：提供设备节点；若挂载失败但已有 /dev/console，允许沿用已有设备挂载。不是无条件忽略所有挂载错误。
4. devpts：伪终端接口；tmpfs /run：运行时临时数据；hostname：设置目标名称。
5. 调用 `/usr/bin/bsp_demo autostart`，必须晚于 proc。

`|| exit 1` 用于前面关键设施准备失败的路径；应用失败时本教学脚本打印 `[INIT] bsp_demo FAILED`。最后的 `initialization complete` 本身不证明应用通过，验收看具体程序输出和错误信息。

为什么应用可以运行？内核和目标库提供所需执行环境；init 调脚本，Shell 解析脚本，脚本执行目标 ELF。不能把“内核直接解释 rcS”当成执行链路。

## 4. 内核构建脚本

[scripts/build-kernel.sh](../scripts/build-kernel.sh#L1)

```bash
#!/bin/bash
set -euo pipefail
source "$(dirname "$0")/env.sh"
make -C "$SRC/linux-6.1.11" O="$OUT/build/linux" ARCH=riscv CROSS_COMPILE=/workspace/riscv-env/linux-gcc11/bin/riscv64-unknown-linux-gnu- quard_star_defconfig
"$SRC/linux-6.1.11/scripts/config" --file "$OUT/build/linux/.config" --disable FTRACE --disable GCC_PLUGINS
make -C "$SRC/linux-6.1.11" O="$OUT/build/linux" ARCH=riscv CROSS_COMPILE=/workspace/riscv-env/linux-gcc11/bin/riscv64-unknown-linux-gnu- olddefconfig
make -C "$SRC/linux-6.1.11" O="$OUT/build/linux" ARCH=riscv CROSS_COMPILE=/workspace/riscv-env/linux-gcc11/bin/riscv64-unknown-linux-gnu- -j"$JOBS" Image
cp "$OUT/build/linux/arch/riscv/boot/Image" "$OUT/images/Image"
cp "$OUT/build/linux/.config" "$OUT/images/linux.config"
```

阅读重点：

- source env.sh：设置本工程源目录、输出目录和工具路径。
- 第一次 make：从上游 quard_star_defconfig 得到实际配置。
- scripts/config：在生成的 .config 中关闭本次不使用的 FTRACE/GCC_PLUGINS，没有改上游 defconfig 源文件。
- olddefconfig：补全配置关系。
- make Image：用明确的 Linux GCC 11 前缀编译，O= 将中间产物放在独立目录。
- 最后两条 cp：把 Image 与实际配置放入约定产物目录。vmlinux 留在 output/build/linux 供调试。

只运行配置命令不等于内核编译通过；编译通过也不等于目标能启动。这两层本项目都通过实际日志区分记录。

## 5. 从文件到镜像

[scripts/make-images.sh](../scripts/make-images.sh#L1)，重点读以下数据流：

```text
app/bsp_demo.c ──交叉编译──> output/bsp_demo
rootfs/ 配置 + BusyBox 安装 + 目标库 + 应用
                         ↓
                 output/rootfs 目录
                         ↓ mke2fs -d
                    rootfs.ext4

Image + DTB + boot.scr ──mcopy──> bootfs.fat
bootfs.fat + rootfs.ext4 + MBR ──pack-images.py──> disk.img
```

脚本中的关键命令（节选）：

```bash
mkfs.fat -F32 -n BOOT "$OUT/images/bootfs.fat"
mcopy -o -i "$OUT/images/bootfs.fat" "$OUT/images/Image" ::/Image
mke2fs -q -t ext4 -b 4096 -O ^orphan_file -L rootfs  -E root_owner=0:0 -d "$OUT/rootfs" -F "$OUT/images/rootfs.ext4"
```

都是对本工程普通文件操作。mcopy 直接操作 FAT 镜像；mke2fs 的 -d 将目录内容填入文件系统，无需挂载分区。脚本显式关闭 orphan_file，采用较保守的文件系统特性组合。当前 Linux 6.1.11 源码实际包含 ORPHAN_FILE 支持，因此不能把这一开关解释为“本内核不支持它”；这也不是关闭数据校验。该选项不作为本项目独立成果。

### Python 打包器只需要看两个概念

[scripts/pack-images.py](../scripts/pack-images.py#L1)

**固件布局**：按上游偏移写入每个组件，写前检查大小不超过预留槽位。你只需知道打包偏移必须与加载器一致，不必背所有数字。

**磁盘分区**：第一分区 FAT32，第二分区 ext4；写入 MBR 后把两个文件系统镜像复制到各自分区起始位置。Linux 中 /dev/vda2 正是这块 virtio 磁盘的第二分区。

```python
# 节选：start 是扇区号，512 是本镜像约定的扇区字节数
for _, _, start, _, name in parts:
    disk.seek(start * 512)
    with (images / name).open('rb') as src:
        shutil.copyfileobj(src, disk)
```

不要把这个 seek 的磁盘偏移与 U-Boot 的 kernel_addr_r RAM 地址混淆。

## 7. GDB 两个小脚本

[scripts/run-debug.sh](../scripts/run-debug.sh#L1)

```bash
#!/bin/bash
set -euo pipefail
source "$(dirname "$0")/env.sh"
# QEMU gdbstub, not KGDB. Bind only to the host loopback interface.
exec "$PROJECT_DIR/scripts/run.sh" -S -gdb tcp:127.0.0.1:1234 "$@"
```

[scripts/debug-kernel.sh](../scripts/debug-kernel.sh#L1)

```bash
#!/bin/bash
set -euo pipefail
source "$(dirname "$0")/env.sh"
exec gdb-multiarch -nx -q "$OUT/build/linux/vmlinux" \
 -ex 'set pagination off' \
 -iex 'set auto-load off' \
 -ex 'target remote 127.0.0.1:1234' "$@"
```

-S 先暂停虚拟 CPU；-gdb 提供宿主调试接口；vmlinux 提供匹配符号。gdb-multiarch 是在宿主上运行的调试器，不是客户机里的 gdbserver。

`-nx` 不读取用户初始化文件；`-iex set auto-load off` 在装入 ELF 前关闭自动加载辅助脚本，减少对隐式配置的依赖。本例的基本断点/源码/栈检查不依赖 lx-* 扩展。

必须理解的目标源码位置：

- [linux-6.1.11/init/main.c](https://github.com/QQxiaoming/quard_star_tutorial/blob/083d2dd8337adc0c7fd0522e1d16e075b9f11365/linux-6.1.11/init/main.c#L936)：进入内核主要 C 初始化流程。
- [linux-6.1.11/init/main.c](https://github.com/QQxiaoming/quard_star_tutorial/blob/083d2dd8337adc0c7fd0522e1d16e075b9f11365/linux-6.1.11/init/main.c#L1423)：参数 init_filename 被作为 argv_init[0]，随后调用 kernel_execve。实测是 /sbin/init。

本次命令和结果见 [evidence/gdb-startup.log](../evidence/gdb-startup.log#L1)。不必背 0xffffffff... 地址；要会按函数名停住，解释 pc/sp/a0 的基本角色，并将参数与下一阶段对应。
