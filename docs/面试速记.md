# 项目速记（应结合运行证据学习）

## 30 秒介绍

本项目基于开源 Quard Star 虚拟板卡，已构建并启动 RISC-V 嵌入式 Linux。复用上游板级支持，构建启动组件、U-Boot、Linux 和 BusyBox；个人定制是修改内核日志等级、编写系统信息 C 程序，并通过 init 初始化脚本实现开机自启动。两轮实际启动、参数对照和程序运行证据见 README 与 evidence。

## 启动链路

```mermaid
flowchart LR
 Q[QEMU quard-star 虚拟硬件] --> R[上游 Mask ROM]
 R --> L[上游 lowlevelboot]
 L --> S[OpenSBI / 上游 Domain 配置]
 S --> U[U-Boot]
 S -. 上游保留的 hart7 .-> T[trusted_domain]
 U -->|Image + DTB + bootargs| K[Linux]
 D[virtio 磁盘根文件系统] --> K
 K --> I[BusyBox init / PID 1]
 I --> C[/etc/init.d/rcS]
 C --> A[bsp_demo autostart]
 I --> H[交互 Shell]
```

trusted_domain 是上游启动基线的一部分，不是本人设计。它与普通世界系统的关系要结合 OpenSBI Domain 配置理解，不应画成“Linux 调用 trusted_domain 才能进入 Shell”的单一路径。

## 十个问答

### 1. QEMU 模拟什么？为什么是 RISC-V？

QEMU 是在宿主上运行的模拟器，本工程用其上游定制的 quard-star 机型模拟 RISC-V CPU、内存、Flash、串口和 virtio 等硬件。RISC-V 是目标 CPU 指令集，运行在其中的固件、内核和应用必须是匹配的目标程序。它能提供无需实板的学习环境，但不证明真实芯片的时序、DDR 初始化或硬件性能。

### 2. 为什么交叉编译？

云宿主是 x86_64，目标是 riscv64，指令集不同。交叉编译器本身在宿主执行，输出 RISC-V 程序；不能拿宿主 gcc 的默认产物直接放进目标系统。`riscv64-linux-gnu-readelf -h` 看 Machine；`readelf -l` 看解释器；在目标 `uname -m` 看实际系统架构。

### 3. 早期固件、OpenSBI、U-Boot 的区别？

Mask ROM 和 lowlevelboot 按上游约定完成最早的启动选择和必要镜像加载。OpenSBI 在 M 态提供 SBI 接口和 Domain 等基础服务。U-Boot 是引导加载器，在本工程中读取磁盘上的内核与 DTB、设置 bootargs，再进入内核。三者职责和运行阶段不同；本项目复用早期固件和板级支持，没有从零实现这些机制。

### 4. M、S、U 怎么分？

M 是机器态，权限最高，OpenSBI 通常在这里工作；S 是监督态，Linux 内核通常在这里；U 是用户态，BusyBox 和 bsp_demo 在这里。早期固件起始于 M 态。本基线 U-Boot 的具体模式应以其 `CONFIG_RISCV_SMODE` 和 OpenSBI Domain 的 next-mode 为证据，不能说“所有 Bootloader 都运行在 M 态”。

### 5. Image、DTB、根文件系统分别是什么？

Image 是 Linux 内核二进制；DTB 是设备树编译结果，向内核描述板卡硬件与部分启动信息；根文件系统提供 init、命令、库和配置等用户空间内容。磁盘镜像是存储容器，可以有多个分区；它不等于 Linux 内核，也不等于 DTB。

### 6. U-Boot 如何加载、传参？

本项目的 `configs/boot.cmd` 使用 `load virtio 0:1` 读取启动分区的 Image 和 quard_star.dtb，设置 bootargs，再用 booti 启动。脚本文本需用 mkimage 包成 boot.scr。bootcmd 是 U-Boot 要执行的引导命令，bootargs 是传给内核的命令行字符串，两者不是同一个东西。最终以目标 `/proc/cmdline` 为准。

### 7. root、console、loglevel 是什么？

root=/dev/vda2 指定 virtio 磁盘第二分区为根文件系统；console=ttyS0 指定串口控制台。本项目选择 loglevel：baseline 为 7，定制为 4，保留原 root 和 console。它控制向控制台输出的内核消息级别，不会让内核停止记录较低优先级消息；`dmesg` 环形缓冲区不等于控制台输出。`/proc/cmdline` 看收到的值，`/proc/sys/kernel/printk` 看当前控制台阈值；boot.log 中无普通 info 输出可作辅助观察。

### 8. BusyBox 为什么有很多命令？

BusyBox 把许多小命令实现为同一个可执行文件中的 applet，再通过不同名称的链接或 `busybox 命令` 分派。它适合小型根文件系统，但不等于完整 GNU 工具集。这里同时提供 init、sh、mount、uname、cat 等。

### 9. 自启动怎么发生？

Linux 挂载根文件系统后启动 PID 1，本项目是 /sbin/init（BusyBox）。init 读取 /etc/inittab，其中 sysinit 项调用 /etc/init.d/rcS。rcS 先挂载 proc、sysfs、devtmpfs，然后执行 `/usr/bin/bsp_demo autostart`。程序读取 /proc/uptime，所以必须放在 proc 挂载之后。一次性执行完成后退出，不是常驻服务；Shell 是后续交互入口，不负责触发这次自启动。

### 10. 自己做了什么，证据在哪？

上游提供板级模型、固件、驱动及默认配置。自己的工作是固定版本与适配云构建流程、组装可启动镜像、修改启动参数、编写 bsp_demo、集成 init 自启动并保存实际日志。程序源码在 app/bsp_demo.c，参数在 configs/boot*.cmd，自启动在 rootfs/etc/init.d/rcS。仅在真实目标日志存在后，才能据此说“已成功启动/生效”。不声称新写驱动、DDR 初始化、设备模型开发或性能优化。

## 程序怎么解释

- `uname(&info)` 获取正在运行的目标系统信息，不是编译机器的信息。
- `fopen`/`fscanf` 读取 /proc/uptime 第一列，单位秒；proc 是内核导出的虚拟文件系统。
- `manual`、`autostart` 只是调用者传入的参数，显示启动来源；自启动是否成立还需观察没有手工输入时的开机日志。
- 返回 0 表示成功；参数错误返回 2；系统调用或文件读取失败返回 1。
- 交叉编译使用目标 libc；动态程序需要 ELF 解释器与目标库。以实际 readelf 和镜像清单说明路径，不背虚构路径。

## 面试表达边界

可以说“基于开源平台完成构建和定制”，不要说“独立移植 RISC-V BSP”。这是入门闭环，项目亮点在于解释清楚每层交接、有可复现入口和真实改动，不在复杂外设数量。
